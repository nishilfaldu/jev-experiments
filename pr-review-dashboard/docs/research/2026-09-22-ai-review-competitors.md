# AI review competitive research

Researched 2026-09-22. Primary sources only. Product analysis, not a code review. No existing research-notes directory was present; this file establishes `docs/research/`. Prices are USD; product pages take precedence over older launch posts. Vendor effectiveness claims have not been independently validated here.

## Decision-relevant conclusion

Natural-language review rules are already a feature in major incumbents. Team libraries, repository scope, review dashboards, and nonblocking checks are also occupied. Just-jevving should not pitch any of these alone as category creation. Its strongest possible distinction is making an explicit question–answer record the product: every rule evaluated against every eligible diff, including negative answers and uncertainty; historical replay; labeled rule-quality evaluation; consumer-controlled thresholds; informational change classification. This is an inference about an opportunity, not a claim that no competitor or adjacent startup offers it.

## Product overlap by name

### CodeRabbit

CodeRabbit already evaluates plain-English custom PR checks, including sensitive logging, migration safeguards, breaking-change documentation, and language-migration policies. It reports structured outcomes and offers warning or error modes. Configuration lives in the dashboard or `.coderabbit.yaml`; a PR command can test a proposed rule before saving it. The March launch post's plan entitlement is older than today's pricing: current pricing places custom checks on Team and above. This is direct overlap with “semantic linter,” not just a generic reviewer that incidentally accepts prompts. [Custom pre-merge checks](https://www.coderabbit.ai/blog/pre-merge-checks-built-in-and-custom-pr-enforced), [current plans](https://www.coderabbit.ai/pricing).

Its analytics show review throughput, cycle metrics, estimated reviewer time saved, comment acceptance, severity and categories. The savings are modeled estimates, not measured counterfactual productivity. Therefore “we have a dashboard and per-rule stats” needs a sharper claim than analytics generally. [Analytics announcement](https://www.coderabbit.ai/blog/measuring-what-matters-in-the-age-of-ai-assisted-development).

Its September 18, 2026 Triage launch also occupies attention routing: workflow state, next action, owner, priority, recommended review depth, saved views, and ranking across PRs. It explicitly separates deterministic workflow decisions from model-assisted comparative ranking. Informational classification is therefore not untouched territory. A narrower opportunity remains arbitrary, user-defined semantic predicates as reusable data. [Triage explanation](https://www.coderabbit.ai/blog/rethinking-pr-triage-from-first-principles).

### Greptile

Greptile positions around understanding the whole repository graph and finding cross-file effects. Its normal output is PR comments with suggested fixes; fixes can be handed to coding agents. Diff-only analysis is a disadvantage against this for bugs whose truth depends on callers, callees, existing middleware, or external contracts. [Introduction](https://www.greptile.com/docs/introduction).

Custom standards are already available at organization/team level, repository level, and cascaded directory scope. Dashboard rules can target selected repositories and file globs. Its documentation tells users to create intentionally violating test PRs and verify detection. This covers basic rule ownership and customization, though the documentation reviewed does not describe a first-class statistical evaluation suite for every rule. [Custom standards](https://www.greptile.com/docs/code-review/custom-standards).

Greptile exposes a 0–5 “confidence score,” but it is a PR-readiness assessment based on issues, complexity, and patterns, not a per-question probability vector. This is an important distinction: don't say competitors have no confidence; say jev could expose uncertainty at the individual decision level. [Review anatomy](https://www.greptile.com/docs/code-review/first-pr-review).

The dashboard already tracks addressed rate, critical bugs, merge times, reactions, and filterable team/repo/author data. TREX adds sandboxed targeted tests and evidence attached to comments. Autoapproval is available in beta for clean, low-risk PRs. These changes put pressure on a product whose only benefit is another list of possible bugs. [Changelog](https://www.greptile.com/changelog).

### cubic

cubic provides plain-English custom agents, optional repository instruction files, file-path filters, attribution on each resulting comment, and a shared rules library. A single definition can apply to several repositories; edits propagate, with per-repo enablement. Its docs explicitly recommend business logic and team conventions that ordinary linters miss. Team rules and per-repository rule sets are thus demonstrated incumbent features. Current pricing advertises five custom agents on Starter/Team and ten on Pro; the docs' blanket five-agent limit appears older, so use the current pricing page for commercial entitlements. [Custom agents](https://cubic-2.mintlify.app/ai-review/custom-agents), [pricing](https://www.cubic.dev/pricing-plans).

cubic frames itself around full repository context, ongoing scans, issue-tracker context, learned review history, and fix agents. It is expanding beyond PR comments into a broader code-maintenance product. These are positioning claims, not proof its detection is superior. [Repository-context positioning](https://www.cubic.dev/blog/choosing-an-ai-code-reviewer-with-repository-wide-context).

### GitHub Copilot code review

GitHub positions it as a first-pass reviewer that comments at relevant lines, suggests fixes, and hands work to the cloud agent; the native distribution and bundled subscription make “one more AI reviewer” hard to charge for independently. [Code review product](https://github.com/features/copilot/code-review).

It supports repository-wide and path-specific instructions, root `AGENTS.md`, other agent instruction formats, repository skills, and MCP context. Reviews can run automatically and rerun on pushes. Its approval capability is in public preview and off by default. This product is much more configurable than a generic chat prompt. [Using code review](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review).

### Semgrep AI

Do not caricature Semgrep as only AST syntax matching. Its current product combines deterministic analysis, cross-file taint analysis, AI detection, AI triage, and remediation. User-authored natural-language Memories encode local facts such as framework protections and test environments to distinguish real security findings from noise. [Pricing/features](https://semgrep.dev/pricing/), [user Memories analysis](https://semgrep.dev/blog/2026/inside-the-ai-memories-security-teams-are-writing/).

Semgrep Workflows combine Python orchestration, deterministic tools, LLM reasoning, local security context, and custom policies. Triggers include PRs, scheduled scans, and APIs. This overlaps heavily with a future “diff questions as a policy engine” feature, especially if positioned toward AppSec. It does not prove a zero-setup, arbitrary-question probability interface exists there. [Workflow documentation](https://semgrep.dev/docs/workflows/overview).

## What is shared, and what might still be distinctive

An adjacent competitor makes the overlap even stronger: **Qodo Rules** already markets an organization/repository rules library, rule-health management, export to other AI tools, and adoption/violation trends. Its September 1, 2026 lifecycle article describes natural-language authoring, compliant/noncompliant examples, categories/severity/scope/provenance, mining review history, deterministic scope selection, and per-rule 30-day counts for compliant results, violations, and merged unresolved violations. Thus even negative outcomes, rule-as-object design, and longitudinal rule measurement are not greenfield. The more specific differentiation would have to be decision-model probabilities, empirical calibration, economical batch/replay, and non-violation questions—not “rules with a lifecycle” by itself. Qodo's “deterministic” marketing should not be mistaken for proof of deterministic semantic judgments; its detailed article specifically describes deterministic rule selection. [Qodo Rules](https://www.qodo.ai/qodo-rules/), [Rules lifecycle](https://www.qodo.ai/blog/how-qodo-builds-the-wisdom-to-govern-part-2-the-rules-lifecycle-system/).

The shared pattern is codebase/context ingestion → automated analysis → prioritized findings → feedback/fix action in the developer workflow. The products increasingly add configuration, organization memory, analytics, policy, and remediation. They do not all work identically: Semgrep's static-analysis foundation differs from agentic reviewers; CodeRabbit combines AST/SAST integrations with AI; Greptile's TREX actually executes tests. Their common commercial promise is reducing review or security work, not exposing decision science.

My product inference: the strongest narrower proposition is **a measurable library of questions about code changes**. A rule has an owner, scope, version, examples, labeled outcomes, evaluation counts, false-positive/false-negative rates, calibration, threshold policy, and a history of which immutable diffs were evaluated. Store the full yes/no distribution and distinguish not evaluated, out-of-scope, missing context, and uncertain. Feed those records into any workflow.

Informational examples: “Does this change customer-visible behavior?”, “Does it change data retention?”, “Does it introduce a schema migration?”, “Does it touch the old payment client?”, “Does it alter an external API contract?” These support release-note selection, reviewer routing, migration tracking, and change intelligence without accusing an author of a violation. They still need empirical validation, correct denominators, and useful consumers. A standalone dashboard with no habitual destination risks becoming an abandoned inbox.

I did not find public documentation in this bounded review showing the incumbents' core product as a complete per-rule × per-diff probability ledger with negative results and labeled calibration/replay. That is weaker and more defensible than claiming nobody has built it. A strong demo should make that unit of value visible; a strong later feature should export it and fit a workflow that already has users.
